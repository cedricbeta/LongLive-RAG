# Feedback v2：等待空闲 GPU 的四例实验

用户已授权在有空闲卡时运行几个案例，检查相对于原版和 v1 是否有进步。

## 已启动

- 目录：`videos/feedback_repair_v2_20260916/`
- 后台 worker PID：`1355756`，实际状态见该目录的 `progress.json`。
- 启动时四张 GPU 均有其他计算进程，worker 已进入 `waiting_for_gpus`。
- 每 30 秒检查一次；连续两次满足条件、取得本项目的 GPU 协作锁并再次检查后才启动。
- 使用两张不同的空闲卡：重画卡剩余显存至少 75,000 MiB，检查/规划卡至少 70,000 MiB，均无其他计算进程且 GPU 利用率不超过 5%。
- 每个案例单独启动检查服务，结束后清理本 worker 启动的进程组、释放锁，再等待下一例所需资源。
- 启动检查服务期间若重画卡被其他任务占用，会释放自己的服务并重新排队。

顺序为 Iris 头发（`ns090`，重点第 3 镜头）、Clara 衣服（`ns310`）、补回 Luna（`ns020`）、原本无需修复的对照（`ns130`）。每例仍运行完整场景，以建立人物参照和检查后续影响。

本次运行开始前冻结当前源码和上轮实验的输入，共核对 357 个源文件/输入/对照产物。baseline、原版和 v1 使用已完成的归档结果，并固定文件哈希；只运行 v2。

力度统一 1.0，每镜头最多 3 次编辑，检查最多 2 个受影响的未来出场；每镜头修复新尝试时间预算 1,800 秒，每案例进程上限 5,400 秒，沿用上次预算。失败、超时和未运行案例都会保留，不自动替换案例或隐藏重试。

## 产物

- `manifest.json`：冻结输入、源码、对照结果和预算。
- `progress.json`：worker 状态、GPU 占用、当前场景和耗时。
- `runs/feedback/<scene>/status.json`、`driver.log`、`<scene>/ledger.jsonl`：每例状态和完整执行记录。
- `comparison.json`：验收结果、实际编辑次数、规划动作、参数是否变化，以及 v2 是否与旧视频字节相同。
- `comparisons/<scene>.mp4`：四格视频，上排 baseline/原版，下排 v1/v2。
- `index.html`：每例完成后刷新，全部结束后再汇总。

入口脚本：`scripts/queue_feedback_repair_v2.py`，后台运行的是 `source_feedback/` 内冻结版本。

排队和相关规划测试共 19 项通过。此前修复流程测试为 106 项与 9 项子测试通过。当前尚无 v2 新视频结果；自动验收计数不能替代画面质量复核。这些案例是根据 v1 结果选择的开发案例，不是独立留出评测。
