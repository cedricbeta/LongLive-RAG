## 3. 拟验证的方法与贡献边界

生成器权重保持固定，称推理时纠错。方法以逐项约束诊断、有限动作、部分改善保留、一致状态继续生成及后续保护组成；其价值需要消融和真实视频验证。

1. **诊断可以驱动真实修复。** 从允许的脚本输入自动构造实体/时间/属性约束，输出 pass/fail/unknown 与证据；区分明确错误、观察不足和判断冲突。unknown 不算 pass，漏掉的要求不从评测分母消失。
2. **有效修复可以累积。** 分开“当前最好分支”和“完整通过分支”；目标确实改善、未新增超过容差的退化时保留部分改善，再修剩余项。固定原始脚本与身份锚点，未核验身份不直接进入可信记忆。
3. **后续生成保持一致。** 候选基于当前最好父分支，mask 与父视频/坐标绑定；一致维护 latent、KV、文本、随机数、检索和身份状态。修改 MP4 不算修改生成状态。replay 的实际成本全部入账。
4. **反馈优于重复尝试。** 力度固定 1.0，保留可靠首次配方；失败后从有限合法范围/文本表达动作中选择，程序依据实际 mask、prompt、seed 判断重复、预算和停止。只有等预算净收益才支持反馈有效。
5. **目标修好而其他内容得到保护。** 成对看父版/候选真实画面，核对身份、非目标属性、动作、其他角色和后续。有限 H=2 不是全片保证；最终评估必须独立于规划/接受器。

IAMFlow 已有 LLM/VLM 协作，VideoRepair 已有视觉检测与局部修复；这些本身不能写成我们的新贡献。应证明“长视频状态上的渐进净修复”超出已有记忆、局部纠错和更多计算的效果。

## 4. 公平比较是实验本身，不是论文措辞

主 baseline 为官方 LongLive 1.3B、LongLive-RAG、MemFlow、IAMFlow。关键比较为 **官方 RAG±Ours、官方 IAMFlow±Ours**；每一对保留相同生成器和纠错前分支。只有一个系统完成时据实限制结论。

本地 A/B/C、5B 与 16 秒历史视频保留为开发证据，不能改名成官方方法。每种官方方法先建立代码/权重/配置 manifest，原生运行、正确时间轴、OFF/zero-mask 和状态传播核验；已有有效适配直接复用，不重复造轮子。

系统表保留各官方机制并披露容量/精度/VAE；模块归因另做同 checkpoint 受控实验。匹配输入文本、参考信息、未来提示可见性、mask 自动化、开发调参预算与最终评分器。不能给 Ours 人工帮助而称自动方法。

同预算对照必须含固定局部重试、Best-of-N、prompt-only feedback、VideoRepair 长视频适配及完整 Ours。相同尝试次数不等于等预算；检测、分割、LLM/VLM、生成、筛选、replay、后续检查和所有设备成本都记账。最终评分器不得参与选候选。

## 6. “比他们更优”的定量验收

以下是**待开发校准的研究目标，不是已完成结果**：最终确认错误负担相对下降至少 15%，EG 增加至少 2 分；同时 Overall 下降不超过 0.5 分，预定质量项下降不超过 1 分、DD 不超过 2 分，新错误率不超过 1%。用开发噪声与人工判断校准一次，测试前冻结；不得按正式结果改阈值。

确认性结论还需要：主要差值置信区间支持收益，质量保护通过预定非劣检验，unknown/保守未解决负担不恶化；同预算赢过固定重试/采样及直接纠错对照，独立评价支持方向。只均值升、只 p 值显著或“退化不显著”都不够。

以脚本配对、多种子脚本内聚合、模板分组统计，处理主要比较的多重检验。不得把相邻帧当独立样本扩大 N。正式结果允许否定假设：只赢单次 baseline 就写计算折中，只赢发色就限定发色；未通过保护不能称安全修复。不能先写出胜利结论再挑证据。

## 7. 推进顺序：先取得有决定性的结果

**第一步：补复现缺口。** 核验官方配置、权重与完整 evaluator，先跑通真实 60 秒。注意 IAMFlow 默认配置与论文加速配置不同；公开 FP8 页面只有 README 不等于有权重。遇阻继续做 RAG 的独立工作，不伪造替代 baseline。

**第二步：有界 pilot。** 已暴露开发池事前选 12 条、1 seed、60 秒，跑 native/固定局部重试/Best-of-N/Ours，测净错误、EG、保护和成本。每轮围绕一个失败假设，给真实视频和数值；不在同一案例上无限添加 schema、judge 提示词或复核分支。没有有效候选时先修执行能力，有候选但拒绝时用独立证据定位接受器，不靠放宽规则制造成功。

**第三步：根据证据冻结。** 如果反馈未赢固定重试，改方法或收窄主张后再做新开发验证；不是加大循环。冻结配置、暴露/测试清单、预算、评分器、统计与异常规则。先算整套 GPU/API/人评预算；T1 单 seed 已有 2,268 个系统输出，T2 最低四行三个长度为 1,536 个，不能用 demo 成本代替预算规划。

**第四步：跑正式表和独立验证。** 优先 T1 核心配对与 T3，再做长度、必要消融、跨 judge 和人评。保留失败、回退、超时；正式 bug 修复按统一规则覆盖全部受影响方法。没有真实人评就标未完成。

**第五步：组织论文与交付。** 主文以问题、方法、定量主表、机制证据、成本与局限展开；每张定性图对应可追溯样本，给 baseline/最强预算对照/Ours 和后续片段，另有普通/失败案例。正文不按开发日期罗列审计历史。

持续推进真实方法与实验；仅为解决关键状态/控制风险写测试。保护已有工作区修改、历史冻结结果及他人进程，使用可用 GPU，记录成本，不做无关重构。
