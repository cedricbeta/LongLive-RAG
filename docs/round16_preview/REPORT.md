## Design & methodology — how each piece is built

The experiment isolates one question: **does letting a VLM rewrite the shot prompts and/or choose which past frames to re-inject into the KV cache improve cross-shot consistency, without cheating?** Below is the full pipeline.

### 1. Generation substrate (identical for all arms)

One long multi-shot video per scene, produced by the **Wan2.2-TI2V-5B** causal video diffusion model:

- **Length / structure**: `num_output_frames = 480` latent frames = **60 blocks × 8 frames** (`num_frame_per_block=8`), partitioned into **8 shots** via each scene's `shot_durations.txt` (e.g. African savanna = `12 12 6 6 6 6 6 6` blocks). At 24 fps the decoded clip is ~20 s.
- **Attention window**: `local_attn_size = 32` frames — the model only attends to the most recent 32 frames, so content from shots more than ~32 frames back has *left the window*. `frame_seq_length = 880` tokens per latent frame (44×80÷4 at 5B).
- **Shot boundaries**: a scene-cut text prefix is prepended at each new shot; `multi_shot_sink` pins the opening frames as an attention sink and `multi_shot_rope_offset` shifts RoPE phase per shot.
- **Decode**: chunked Wan VAE → MP4. **One seed (0)**; arms are paired against the same-seed baseline so the only variable is the intervention.
- **Baseline arm**: KV-RAG and prompt-refine both OFF. It is *reused* from the earlier frame-level run — `videos/frame_strategy_A/baseline_seed0/baseline_seed0-rank0-<scene>-seed0_regular.mp4`, generated by `videos/frame_strategy_A/configs/baseline_seed0.yaml` via `inference.py` (Wan 5B, 480f, local_attn 32, `kv_rag.enabled=false`, seed 0).

### 2. The two optimizer levers (driven by Qwen3-VL)

The local **Qwen3-VL-8B** optimizer watches the baseline render of a scene **once**, diagnoses *which shot cut broke consistency and how*, then emits two things per scene (`optimizer_decisions.json`):

**(a) Prompt-refine** — it appends invariant descriptors to the scene's `global.json` (which is prepended to every shot caption). Constrained to **ADD** subject/scene invariants only; forbidden to delete per-shot camera/action or collapse shots to identical text. Example (savanna): it added *“…viewed from inside a safari vehicle with visible interior frame and windshield bars.”* See per-scene diffs below.

**(b) KV frame selection** — it produces an *anchor plan*: at each shot boundary, which earlier **decoded frames** to inject as persistent scene-memory (`manual_anchor_plan.json`, source `qwen3_vl_decoded_frame_plan`; cap 2 frames/boundary). KV-RAG then injects those **whole latent frames** into the cache. Verified injection mechanics for `both`/savanna (`*_kv_rag_diag.json` `pos.stats`):

| quantity | value | meaning |
|---|---|---|
| boundary_injections | 120 | injection events across the rollout |
| injected_frames | 220 (of 240 requested) | whole frames re-inserted; 92% of Qwen's picks matched an available stored frame |
| injected_tokens | 193,600 | = 220 × 880 → exactly frame-aligned (`frame_alignment_inject_drops=0`) |
| outside_window_injected_frames | 220 | every injected frame came from a shot already outside the 32-frame live window (so it adds memory, not redundancy) |
| reinject_rope_injection_calls | 120 | injected keys re-RoPE'd to sit just before the live window (in-distribution positions) |
| persistent_rag_attention_mass_mean | **0.0141** | the model gave injected memory only ~1.4% attention — same as Round 14; it barely *reads* the memory |
| persistent_logit_bias_calls | 0 | the attention-boosting logit-bias lever was OFF this round |


**§2.1 — what was actually injected vs what Qwen proposed (a known confound).** The bracketed values are **lists of frame indices, not ranges** (`[0, 95]` = frame 0 and frame 95). Two mismatches to be aware of:
- **Qwen's own output is internally inconsistent**: for several scenes the structured `decoded_frame_indices` stays e.g. `[0, 95]` across boundaries 2–7 while its rationale prose enumerates ever more frames (0, 95, 96, 191, …). The per-scene tables below show the structured field.
- **A single shared plan was injected for all scenes**, not each scene's own proposal. The injected `manual_anchor_plan.json` (`source: qwen3_vl_decoded_frame_plan`, `anchor_cap=2`, "per-boundary union/quantile … snapped to available whole-frame entries") is:

| boundary | injected frames |
|---|---|
| 1 | [0] |
| 2 | [0, 95] |
| 3 | [0, 191] |
| 4 | [0, 287] |
| 5 | [0, 383] |
| 6 | [0, 95] |
| 7 | [0, 95] |

So the KV arms did **not** inject truly per-scene Qwen selections — they injected this one aggregated plan everywhere. Fixing this (true per-scene injection + reconciling Qwen's structured output with its rationale) is on the Round 17 to-do (AC-5).


This is the key mechanistic finding: the **frame-level contract holds** (whole frames, in-distribution positions, sourced from outside the window) yet the model still down-weights memory to ~1.4%. Dose/placement is not the limiter.

### 3. The four arms

| arm | prompt | KV scene-memory |
|---|---|---|
| `baseline` | original | off |
| `prompt_only` | Qwen-refined (added invariants) | off |
| `kv_only` | original | on (Qwen anchor plan) |
| `both` | Qwen-refined | on (Qwen anchor plan) |

KV config (kv_only/both): `scene_memory_enabled`, `injection_schedule=boundary`, `rolling=true`, `boundary_inject_anchors=2`, `retrieval_key_mode=pooled`, `retrieval_value_mode=raw`, `reinject_rope`, frame-aligned store/inject.

### 4. The judge (held-out, closed model)

- **Model**: GPT-5.5, reached by **reusing the codex OAuth login** (no paid API key; `~/.codex/auth.json`). Claude OAuth was the intended primary but hit HTTP 429.
- **Input**: per video, **1 frame sampled per shot (8 frames)** shown in order (`judge_frames/<scene>/<arm>/`).
- **Output (strict JSON)**: `subject_identity_preserved`, `background_coherent`, `per_shot_adherence[]`, `which_cut_broke + how`, `cheat_flags{copy_cheat,freeze_cheat,prompt_collapse,position_bias_suspected}`, and an `overall_consistency_score`.
- **Win rule**: an arm *wins* a scene if its overall score beats the same-seed baseline.
- **Validated before use** (degrade fixtures): subject-swap → identity scored 0.15 (low ✓); copy/freeze → cheat flagged ✓; viewpoint-only change → not penalized ✓; shuffled pane order → no spurious flag ✓; repeat-run → stable ✓. So the judge discriminates correctly.

- **Separation**: the judge (GPT-5.5) and the optimizer (Qwen3-VL) are different models with no shared context, so the optimizer cannot game its own grader.

### 5. Numeric guards (anti-reward-hack) and the PASS rule

A judge win is necessary but **not sufficient**. A PASS additionally requires clearing orthogonal numeric guards the judge cannot game by degenerate behavior:

- **Motion** — RAFT `dynamic_degree` non-regression (tol 0.2): blocks winning by freezing motion.
- **Diversity** — `inter_shot_composition_diversity` non-collapse: blocks winning by making shots near-identical.
- **Adherence** — per-shot CLIP score non-regression (tol 0.02): blocks ignoring the prompt.
- **Consistency metric** — `anchor_drift_aggregate_consistency` (DINO subject + CLIP background anchors).
- **Negative control** — a degraded/ill-posed input must NOT pass.

**PASS = judge wins on ≥⌈N/2⌉ scenes AND all numeric guards clear AND sane negative control.** In Round 16 the judge passed but the guards did not — diversity dropped 4–20% and motion 21–26% on the winning arms — so the result is an honest null, and the guards are what caught the reward-hack.

### 6. Loop structure (this round)

Round 16 was **single-pass**: baseline → Qwen3-VL reads it once → one prompt-refine + one anchor-plan → regenerate the three arms → judge once. The design allows up to 3 iterative refine→regenerate→re-judge rounds; those (plus the logit-bias lever) were left for a follow-up.
